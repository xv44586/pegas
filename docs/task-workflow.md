# 事情从发起到交付

适用范围为 Chat、事情列表和详情、待你处理、交付审查。沿用 Task、Run、Goal、Approval、Action、Outbox 和 Automation 的职责。以 Control Plane 返回的事情状态和当前可用动作作为跨端交互合同。

## 审计与实施顺序

| 环节             | 发现                                                                                                                   | 修复与验收                                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 发起与排队       | 入站消息、已排队 Run 和执行中容易混在一起；本页排队消息刷新会丢，失败会反复自动发送，编辑可能改发到当前选中的其他事情  | 区分事情创建、排队和执行；在当前浏览器标签页保留待发稿及原目标，失败待用户重试，不静默丢弃                                           |
| 执行与等待       | 列表、托盘和详情各自以 Run 或原因字符串判定；历史失败 Run 会覆盖当前事情状态；审批、澄清、依赖、证据和核对共用模糊提示 | 服务端投影当前状态、关联待办或 Run；历史尝试独立展示，当前动作进入对应的既有入口                                                     |
| 失败、停止与恢复 | 停止显示为归档；审批或核对阻塞时仍可能出现重试；已停止详情仍提示等待                                                   | 只针对服务端允许的 Run 重试；停止始终有明确永久语义；未知动作仍可核对                                                                |
| 交付与下一步     | 历史卡片重复生成静态建议；点击会覆盖现有草稿；交付审查没有接受或返工；解释结果会重开工作                               | 当前交付拥有审查与解释入口，历史仅保留其对应结果和引用；只读解释与继续执行分开；明确要求用户验收时，用持久决定接受或退回具体交付版本 |

## 状态和动作

事情投影回答当前正在发生什么、需要谁介入。Run 只描述一次执行尝试。已完成、已移交、未完成关闭和已停止的结论分别显示；已交付但待用户验收的状态由 Goal 与具体 Review Pack 决定。等待审批或核对时，详情优先进入对应待办，保留原有权限门禁。失败重试、结束后的继续执行、新建相关事情和只读解释使用各自入口。

解释结果使用原 Task 或回复的服务端事实、独立只读会话和显式用户请求。继续执行沿用原 Mandate，新授权仍走相关事情和审批。用户验收锁定当前 Goal revision 和 Review Pack，接受是持久事实，退回以说明产生一次有来源的继续输入；旧交付保持可审查。自动验收作为已有 Goal 的兼容默认。

## 边界与恢复

- Router 只判断归属与控制意图，解释和执行由相应 Executor 完成。
- Web 不从文案生成可执行动作或借用上一次 Run 的状态。无服务端投影的旧版本使用兼容展示。
- 审核、重试和恢复的写入口继续校验 owner、状态、权限和幂等。冲突时保留输入和已选择的上下文，提示刷新或重新查看当前事实。
- 本轮沿用现有 Task 状态枚举、原视觉系统及渠道入口。用户未请求暂停时不伪造暂停能力。跨设备待发稿属于后续持久化工作。

## 服务端业务审查（2026-11-25）

审查覆盖已隔离的上一轮改动和主分支上的既有路径。按入站、归属、执行、审批和核对、交付、终态以及恢复追踪读写方与提交边界。回归优先覆盖可导致输入丢失、旧结果被结算或流程长期停放的分支。

| 环节                 | 权威边界及本轮结果                                                                                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 发起、归属与显式回复 | Control Plane 校验 owner 和可引用正文，Inbox 保存用户输入。Router 归类后写入目标 Task。多条输入遇同一个阻塞 Action 时，在同一事务保留整批，逐条释放。                             |
| 执行、纠正与重试     | Run 领取和续租校验 Worker。纠正在完成写回、最终报告和新审批前参与同一写事务。执行中断时恢复原输入、纠正和兼容会话；空转或取代的旧 Run 保留。                                      |
| 等待、审批与协作     | Action 未结算期间，普通补充、指定回复及协作输入等待。版本化输入保留消费契约并停放，原领取者失去续租和完成能力。审批或核对解除后，按目标和阻塞记录重新领取。停止时结清停放的输入。 |
| 证据、交付与验收     | 新尝试原子取代旧证据报告，旧报告保留审计。人工验收绑定当前 Review Pack，查看只记已读。接受才结束事项并记录成功经验；退回保留具体修改要求，转派失败后可重发同一事件。              |
| 后续解释、继续和终态 | 解释从确切结果进入只读会话。继续执行使用原 Task 的授权及运行条件；人工停止永久生效。随后重新开展工作可以新建带来源的事情。                                                        |

### 缺口修复与验收

1. **PLAN-001** 将成功归类的目标、Run 和整批 Inbox 回执同事务提交。中间领取失效时整批不落盘，提交后 Worker 重启不会再次领取其中一条。指向事情的原消息分别关联同一目标。
2. **SCHEDULE-001** 在待验收、返工入队前暂缓既有事情的计划，保留原到期时间。返工入队后恢复；接受或停止关闭关联计划并结清尚未派发的调用。Run 已落盘的调用在恢复后补齐回执，避免重复创建。
3. **SELF-001** 用发布产物的工作流能力独立于 schema 判定升级与回退。待验收和返工、在途指定回复及解释、未消费纠正、来源撤权都会阻止切换到不兼容的 Release。回退前先处理这些活跃工作；保留撤权时使用兼容版本。
4. **TASK-002** 在归类提交时复核当前恢复策略和原始接单来源。受支持的 Web 与 Mobile 同 owner 可跨端续接；任一来源被撤权后，待处理输入保留为可重试失败，原事项保持结束。策略通过认证 API 调整，对撤权前已经归类并提交的 Run 沿用既有审批与执行权限。

基线为 `origin/main fa05da7`。四项修复在各自 worktree 通过 `pnpm check` 与 `pnpm smoke`；集成通过 145 个测试文件、1544 个测试。三个真实进程崩溃场景、新版本接管与故障自动回退、同 schema 拒绝回退并保留撤权，以及 Chromium 桌面和移动端的交付关键路径全部通过。

发布分支在 `origin/main 523e67d8` 上复验，兼容已占用 v54、v55 的记忆迁移，恢复策略使用新增 schema v56。`pnpm check` 通过 148 个测试文件、1562 个测试，常规 smoke 通过。
