# Pegas 产品定位

> 状态：Draft 0.3
> 更新日期：2026-11-20

## 一句话定位

Pegas 是一个以自然对话为统一入口、跨端持续存在、能够把模糊意图共同形成可验证目标，并自动组织、持续执行和证据化交付的个人智能代理。

更口语化地说：

> 你可以从一个还没想清楚的愿望开始；Pegas 帮你形成目标、补齐上下文、持续执行，并拿出可以审查的结果证据。

## 要解决的问题

今天的大多数 Agent 产品仍然要求用户管理系统复杂度：

- 创建和选择 chat、session、thread 或 project；
- 决定使用哪个模型、工具、Agent 或执行模式；
- 在长任务中断后手动寻找和恢复上下文；
- 同时提出多个需求时，主动维护话题边界；
- 在 Web、桌面、手机和消息应用之间重复交代背景；
- 像项目经理一样频繁检查 Agent 是否仍在工作。
- 在开始前自己把模糊愿望整理成完整目标、流程和前置条件；
- 在结束后阅读代码、日志和处理步骤，才能猜测事情是否真的完成。

Pegas 的基本判断是：

> 用户带来意图、判断和最终选择；Pegas 帮助澄清目标、组织上下文、负责执行与生命周期，并用可验证 evidence 让用户审查和纠偏。

系统内部仍然需要 session、context window、worker、queue 和 sandbox，但这些不应成为用户的操作对象。

## 产品承诺

### 1. 一个持续存在的身份

无论从 Web、App、macOS 还是消息渠道进入，用户面对的都是同一个 Pegas。跨端一致不只是同步聊天记录，而是共享：

- 身份与行为方式；
- 正在进行、等待和已完成的任务；
- 用户明确授权保存的偏好和事实；
- 权限、审批策略和执行记录；
- 对当前重点与近期情境的理解。

### 2. 对话就是入口

用户不必先判断一条消息属于问题、任务、补充条件、灵感还是周期事项。Pegas 自己决定应该直接回答、建立任务、关联旧任务、暂存 idea、设置触发条件，或提出一个真正必要的问题。

### 3. 与用户共同形成目标

Pegas 不假设普通用户已经知道自己的准确目标、全部上下文、前置条件和验收方式。用户可以从一个愿望、问题、抱怨、例子或一段语音倾倒开始。实际 Executor Agent 在检查真实工具、权限和环境后：

- 区分最终结果与现有流程，不把填表、发邮件或运行命令误当成目标；
- 识别会改变结果、成本、权限或风险的关键未知项；
- 一次只提出真正必要的问题；
- 形成包含完成条件、非目标、来源、假设、前置条件、权限和 evidence plan 的 Goal Contract；
- 在目标扩张或关键假设变化时，让用户重新判断，而不是静默改变责任范围。

即时问答和明确的低风险任务不需要仪式化访谈。Goal Contract 是服务端内部的目标与验收合同，不是要求用户维护的新项目管理表单。

Router 仍然只负责输入属于哪个 Task 或控制意图；目标澄清、工具判断和用户可见答复属于实际 Executor。

### 4. 混乱的对话，清晰的任务

用户可以任意插入新话题，后台必须把它们分流成独立、持久的任务上下文。

例如：

```text
用户：帮我研究一下个人知识库方案。
用户：对了，下周提醒我续费服务器。
用户：刚才那个知识库最好还能接 Telegram。
用户：我突然想到 Pegas 可以有情绪状态。
```

Pegas 应识别为：

1. 创建“个人知识库方案”任务；
2. 创建有时间触发条件的“服务器续费”任务；
3. 把 Telegram 支持合并到知识库任务；
4. 保存一条可以以后讨论的产品 idea。

统一对话入口不等于把一切塞进一个无限增长的上下文。

### 5. 持续执行

Pegas 接管的是完整生命周期，而不是一次模型调用：

```text
意图进入
  → 识别与归属
  → 建立或更新任务
  → 形成或修订 Goal Contract
  → 规划执行方式
  → 调用工具或执行单元
  → 持久化进度
  → 在关键节点汇报或询问
  → 收集与完成条件对应的 evidence
  → 交付 Review Pack
  → 沉淀必要记忆
  → 按需继续维护
```

任务可以跨越数分钟、数天甚至更久，并且在进程重启、设备离线、部署升级或工具暂时失败后继续。

“持续存在”描述的是产品体验，不意味着 Agent 必须持续占用模型和执行资源。Pegas 平时可以休眠，在以下事件发生时被唤醒，完成一段有边界的工作后再次休眠：

- 用户发来新消息或补充条件；
- 到达约定时间或周期；
- 外部系统状态发生变化；
- 用户回答问题或完成审批；
- 依赖的 Task、Action 或 Run 产生结果。

因此，Pegas 的 always-on 能力来自持久状态、可靠事件和可恢复执行，而不是一个永不结束的 session。

### 6. 有意义的主动性

Pegas 不应持续发送“仍在工作”之类的噪声。默认只在以下时机主动联系用户：

- 出现可供判断的阶段成果；
- 遇到无法自行解决的阻塞；
- 需要改变目标、成本或风险边界；
- 即将执行敏感或不可逆操作；
- 任务完成或失败；
- 用户关心的外部状态发生重要变化；
- 到达双方约定的时间或周期。

### 7. 用 evidence 交付，而不是用过程证明忙碌

用户 Review 的默认对象是 Task/Goal 是否完成的 evidence，而不是 Agent 写了哪些代码、调用了哪些工具或经过了多少步骤。

- **Execution Trace** 回答 Agent 做了什么、何时做、哪里失败和重试，保留在 WorkChannel、Run 和审计记录中；
- **Delivery Evidence** 回答每个完成条件是否达成、凭什么相信、还有什么未证明，通过 Review Pack 和 Outbox 交付；
- 代码 diff、命令输出和工具日志可以作为审计线索，但除非 Goal 本身要求审查实现，否则不应成为默认交付界面；
- Agent 总结、自由文本 `ready` 和退出码不能独立证明完成；缺少证据的条件必须标记为 partial、unverified 或 failed；
- 图片、视频、UI 和排版发生变化时，最终截图、关键帧或页面渲染是必需 evidence，并绑定准确 Artifact revision。

Review Pack 按 success criteria 组织 evidence、限制、剩余风险和回滚，不按执行时间线罗列动作。用户可以从 Review Pack 按需进入 Channel 查看完整过程，但不必先理解过程才能验收结果。

### 8. 可控、可信、可追溯

Pegas 会逐渐接触文件、账号、浏览器、代码、邮件和日历。安全不能只依赖提示词中的“请小心”，而必须落实为代码执行的权限边界。

建议的默认风险等级：

| 等级           | 行为                                       | 默认策略                   |
| -------------- | ------------------------------------------ | -------------------------- |
| 低风险         | 搜索、读取、分析、整理                     | 可直接执行                 |
| 可恢复写入     | 创建草稿、本地工作文件、运行测试           | 执行后通知                 |
| 外部副作用     | 发消息、创建日程、发布内容、修改远端数据   | 执行前确认或按明确规则授权 |
| 高风险或不可逆 | 付款、删除重要数据、生产环境操作、扩大权限 | 强制确认并保留审计记录     |

### 9. 能够安全地演进自己

修改 Pegas 自身也是一项受管理的 Task，而不是对正在运行目录的一次直接覆盖。Pegas 可以根据用户提出的 feature 创建隔离开发环境、修改代码、执行验证并生成候选版本；独立的发布与恢复系统决定候选版本能否接管服务。

自我更新必须满足与其他高风险 Action 相同的可追溯性，并额外具备版本化构建、健康检查、观察期、自动回滚和独立恢复入口。代码发布成功后，原 Task 从持久状态继续，而不是依赖旧进程保存上下文。

## 用户心智模型

用户只需要理解三个概念：

- **Pegas**：长期存在的搭档；
- **事情**：想让 Pegas 处理的目标、责任或灵感；
- **确认**：Pegas 在需要用户判断或授权时发出的请求。

“Channel”是事情的可选深入视图：用户可以从列表进入一件工作的完整记录并直接纠偏，但不应被要求先创建、选择或配置 Channel、Worker、模型或 session 才能和 Pegas 对话。服务端仍以 Task 保存权威生命周期，Channel 是面向用户的产品投影。

用户也不需要理解 Goal Contract、EvidenceRef 或 Review Pack 这些内部对象。日常体验只表现为：Pegas 帮忙把事情想清楚；需要判断时给出简短确认；完成时拿出与目标对应的证据。

## Web 交互模型

Web 客户端采用同一个产品的三层信息深度，而不是把对话和任务管理拆成互不相干的入口：

1. **默认是 Pegas 主对话**：用户进入后直接表达任何事情。Pegas 的计划、运行、等待、委派和结果以克制的系统事件或消息自然出现，不要求用户先选择项目或创建工作项。
2. **按需进入 WorkChannel**：左侧 Channel 列表和主对话中的事件可以打开一件工作的完整记录。进入后，用户输入显式归属于该 Channel，并由当前 Worker 继续处理；底层 Run 或 session 可以轮换。
3. **右侧工作区负责下钻**：点击 Channel 事件、委派关系、Artifact 或 evidence 时，桌面端先在右侧工作区展示完整过程与详情，移动端进入完整详情。代码、工具调用和执行日志默认留在这一层。
4. **Outbox 聚合判断与验收**：需要确认、阻塞、失败和重要结果进入 Outbox；Task 完成时优先展示按 success criteria 组织的 Review Pack 和可预览 evidence，普通 progress 和内部上下文传递不打扰主对话。
5. **信息深度可以增加，交互心智不变**：Channel 和 Outbox 用于检查、纠偏和接管，不是日常使用的前置步骤；返回后用户仍面对同一个 Pegas。

这一结构允许默认体验保持简单，同时为多任务协作、审批、Artifact、日志、定时事项和自我更新过程保留足够的可检查空间。完整交互与协作边界见 `docs/channel-worker-collaboration.md`。

## 内部核心对象

### Conversation Event

来自任意渠道的一条输入或输出事件。它是交互记录，不是工作隔离边界。每个事件应保存来源、身份、时间、可见范围和与任务的关联。

### Event Inbox

所有可能唤醒 Pegas 的输入都先进入持久化事件收件箱，包括用户消息、时间触发、外部事件、审批结果和其他任务的完成事件。

同一用户的待处理事件先由唯一的 Router 有序归属，避免两条并发消息被错误地创建为重复任务或产生冲突判断；完成归属后，不同 Task 的 Run 可以并行执行。用户连续发送的普通补充可以短暂合并处理，但停止、取消、审批和高优先级纠正必须立即生效。

### WorkChannel

WorkChannel 是 Task 的用户可见投影和工作记录入口，不是新的服务端事实来源。它把目标、用户输入、Router 决策、Run、工具摘要、Artifact、结果和协作关系组织成可搜索、可继续的时间线。第一阶段 Channel 与 Task 使用同一稳定 ID；未来即使投影演进，Task 生命周期仍不跟随某个客户端或 Executor Session。

用户可以进入 Channel 直接和当前 Worker 对话。此时客户端显式携带 Channel/Task ID，不再要求 Router 从全局候选中猜测归属。从 Channel 返回 Pegas 主对话后，新输入恢复自动路由。

完成结束的是当前工作轮次，不是 Channel 历史。completed Channel 保留接单时的不可变 Mandate，在当前 Policy 复核通过且输入属于原目标时恢复并创建新 Run；用户明确停止后的原 Channel 永久不可恢复，继续工作必须重新接单并新建带来源关系的 Channel。复核失败保持 completed，不伪装成人工停止。归档只整理列表，不改变授权或执行状态。

### WorkerProfile

WorkerProfile 是 Pegas 为一个工作范围保存的执行配置，不是独立对外人格。所有 Worker 默认继承用户配置的全局 Agent 模型；只有被明确修改的字段才形成覆盖。每次 Run 保存有效配置快照，运行中的 session 不因设置变化被静默改写。

Worker 不能直接私聊或创建另一个 Worker。它只能向 Pegas 提出委派、交接、上下文传递或 handback 请求，由 Control Plane 校验权限、建立 Channel 关系、投递输入并在完成后把结果送回来源 Channel。

### Task

真正的工作单位。至少包含：

- 目标与完成条件；
- 当前 Goal Contract revision、evidence plan 与完成判断；
- 当前状态与状态原因；
- 相关对话和上下文；
- 计划、执行记录和产生的 artifact；
- 等待的用户、时间或外部事件；
- 下一步动作；
- 风险等级和授权范围；
- 与其他任务的父子、依赖、合并或冲突关系。

目标状态模型保持简单：

```text
Backlog → Unstarted → Started → Completed（可恢复）
            ▲                         │
            └── 用户输入 + 授权复核 ──┘

Backlog / Unstarted / Started ── 用户停止 ──→ Cancelled（原 Channel 永久不可恢复）
```

等待、暂停、最近失败和依赖等待使用状态原因表达；失败属于 Run，不自动结束 Task。Run、Worker Runtime 和 Executor Session 均可结束或替换，而不删除 WorkChannel。

### Run

Task 的一次具体执行尝试。一个 Task 可以先后或并行产生多个 Run，也可以更换模型、Agent、设备或执行环境，而不改变 Task 本身。

Run 负责保存：

- 使用的执行后端和上下文；
- 当前步骤与恢复点；
- 工具调用和执行结果；
- 进度、失败与重试；
- 本次执行产生的 artifact；
- 对外部系统造成的副作用。

Task 状态不能跟随某个 Run 或 session 的存活状态。

### Goal Contract

Task 的版本化目标与验收合同，保存期望结果、完成条件、非目标、来源、假设、未知项、前置条件、权限边界、evidence plan 和失败恢复。它不规定具体 Executor、模型或工具。修订通过新 revision 和事件表达，不能覆盖用户原始意图。

### Evidence 与 Review Pack

Evidence 是支持某个 success criterion 的可检查事实引用，必须绑定准确 Task、Run、Goal revision、Artifact revision 或外部对象，并记录环境、时间、可见范围和限制。

Review Pack 是面向用户的交付投影：逐项显示 `satisfied`、`partial`、`unverified` 或 `failed`，引用 evidence，说明限制、剩余风险和回滚，并提供到 Artifact 与 Channel 审计记录的入口。Review Pack 不替代 Control Plane 的完成事实。

### Memory

记忆不能等同于聊天摘要或向量库。至少分为：

- 用户偏好：沟通方式、常用技术和工作习惯；
- 事实记忆：项目、人物、环境和长期约束；
- 情境记忆：近期重点与临时背景；
- 经验记忆：某类任务过去如何完成、哪些做法有效；
- 敏感记忆：需要单独权限、加密和保留策略的信息。

记忆必须可查看、可纠正、可遗忘，并记录来源。任务的真实状态应保存在结构化任务数据中，不能只依赖模型记忆。

Memory 只保存无法可靠地从事实来源重新获得、并且未来确实有价值的信息。对于文件、邮件、网页、日历和其他外部事实，优先保存稳定引用和必要索引，而不是复制全部内容。

Pegas 默认采用“索引常驻、详情按需加载”的方式组织上下文：当前目标、关键约束和恢复点保持精简可用，历史细节在需要时再检索。任何上下文压缩或 session 替换发生前，都必须先把任务进度、Action 结果和必要记忆写入持久存储。

### Capability

Pegas 可以调度的能力，例如浏览器、文件、终端、macOS 应用、邮件、日历、代码 Agent、搜索、定时器和其他专业 Agent。

模型负责提出调用意图，策略层负责决定是否允许、是否需要审批、在哪里执行以及如何记录。

账号凭证和密钥不进入模型上下文或长期记忆。Pegas 只向执行层表达所需能力，由独立的凭证代理在通过策略检查后为具体 Action 注入最小权限凭证。

### Trigger

使任务重新进入可运行状态的条件，包括时间、周期、Webhook、外部状态变化、用户消息或其他任务完成。

面向用户需要区分两种语义：

- **Follow-up**：围绕当前事情在未来继续一次，例如“明天下午再问我是否发布”；
- **Schedule**：按照明确规则持续发生，例如“每周一整理上周进展”。

二者在底层都可以由 Trigger 表达，但不应在产品体验中混为一谈。调度器只负责把到期条件转成 Event Inbox 中的新事件，不能绕过任务控制直接运行 Agent。

### Approval

Pegas 在执行敏感动作或需要用户判断时创建的结构化等待项。Approval 必须说明准备执行什么、影响范围、可选项和默认建议，并能在进程重启或用户切换设备后继续等待。

等待 Approval 时，Pegas 应保存 Action、恢复点和所需上下文，结束当前 Run 的占用并释放执行资源。用户的回答作为新事件进入 Event Inbox，由新的 Run 从对应 Action 恢复；等待期间，Pegas 仍可继续处理同一用户的其他 Task。

### Outbox

所有需要主动送达用户的结果先进入持久化 Outbox，再由投递层负责去重、排序、重试、合并、静默时段和渠道选择。Task 交付优先携带 Review Pack：用户直接预览 evidence、限制、风险和回滚，需要时再下钻到 Channel。这样即使客户端离线或服务重启，重要结果仍能可靠到达，同时避免把代码、工具调用和内部运行日志变成消息噪声。

## 主要使用场景

第一阶段需要同时覆盖六类行为：

1. **即时问答**：直接回答，不制造不必要的任务。
2. **一次性执行**：研究、整理、写文件或完成一个明确结果。
3. **异步长任务**：后台持续推进，允许暂停、恢复和中途转向。
4. **灵感收件箱**：先接住不成熟想法，随后关联、展开或归档。
5. **持续责任**：根据周期或事件长期维护某件事，而不是每次重新下达命令。
6. **自我演进**：在隔离环境中修改、验证和发布 Pegas 自身，并在失败时自动恢复。

## 第一阶段产品假设

第一版要验证的不是“能接多少工具”，而是：

> 一个用户通过单一对话流交给 Pegas 多个不同类型、甚至尚未完整定义的事项；Pegas 能正确分流、共同形成可验收目标、持续执行、跨重启恢复，并用 evidence 交付结果。

### MVP 必须具备

- 一个主要对话入口，并为其他渠道预留统一事件协议；
- 一个持久化 Event Inbox，将用户消息、时间、审批和外部变化统一为可恢复事件；
- 将新消息归属到现有任务或创建新任务；
- 从自由表达形成可修订的目标、完成条件、关键前置条件与 evidence plan；
- 多任务并行、状态持久化和任务恢复；
- 等待用户输入或审批时释放执行资源，并能从持久恢复点继续；
- 明确区分 Follow-up 与 Schedule 的时间触发能力；
- 结构化进度事件、按完成条件组织的 Review Pack、持久化 Outbox 与安静的通知策略；
- 基础记忆的查看、修改和删除；
- 工具调用权限、审批、凭证隔离和审计记录；
- 一个只读优先、无需用户维护的任务/活动视图。
- 独立于 Pegas 主进程的 Supervisor、健康检查和上一版本回滚能力。

### 暂不追求

- 面向互不信任用户的多租户 Agent 平台；
- 一开始覆盖所有操作系统和消息渠道；
- 让用户手工搭建复杂工作流；
- 无边界的完全自主执行；
- 依靠多个 Agent 的视觉效果来制造“智能感”；
- 用一个超长聊天上下文代替任务和记忆系统。

## 成功标准

早期验证可以围绕以下指标：

- 用户无需指明任务 ID，Pegas 仍能正确判断新建、合并或补充；
- 用户无需预先写出完整目标和验收方案，Pegas 仍能形成可纠正的 Goal Contract，并只询问关键未知项；
- 进程重启后，运行中和等待中的任务不会丢失或重复产生副作用；
- 用户在另一个端继续对话时，无需重新解释目标和任务状态；
- 长任务中的每个外部副作用都有可追溯记录；
- Pegas 主动消息的大部分都能带来决策、结果或风险信息，而非运行噪声；
- 用户可以仅凭 Review Pack 判断每个完成条件是否有 evidence，而不必阅读代码和处理日志；
- 用户可以在一句话内暂停、继续、取消、纠正或查询任何事项。

## 当前产品判断

- Pegas 的 always-on 是由事件唤醒、持久状态和恢复能力构成的体验，不等于持续运行一个 Agent session。
- 所有唤醒来源进入统一 Event Inbox；同一用户先有序路由，再允许不同 Task 并行执行。
- Pegas 应积极推进，但主动程度必须可学习、可配置，并受风险策略约束。
- 默认根据风险决定是否询问，而不是所有步骤都询问或所有步骤都自动执行。
- 用户可能只知道愿望、问题或失败样例；帮助形成目标与验收方式是 Pegas 的核心责任，不是高级模板。
- 用户等待和审批是可持久化状态，不应长期占用 worker 或阻塞其他 Task。
- Memory 应保持精简，以来源引用和按需检索为主；Task 进度永远属于结构化控制面。
- 凭证必须与模型上下文隔离，并按 Action 注入最小权限。
- 主动消息通过持久 Outbox 投递；Pegas 默认安静，只有结果、决定、风险和重要变化值得打扰用户；Task 结果默认交付 evidence，不交付过程日志。
- 修改 Pegas 自身必须生成不可变候选版本，不能修改正在运行的发布目录；发布权属于独立 Supervisor。
- 提供任务中心，但它是可见性与接管界面，不是用户必须维护的项目管理工具。
- 内部可以使用多个执行 Agent，但对外保持单一身份和一致语气。
- Conversation 与 Task 必须从第一天就在数据模型上分离。
- Task 与 Run 必须分离；Task 是用户的目标，Run 是一次可替换的执行。
- 第一阶段使用 DSH 承载模型、session、工具和 Agent 执行，但 Pegas 的任务状态不依附于 DSH session。
- DSH 通过独立适配层接入，产品领域代码不直接依赖具体 runtime API。

## 尚待验证的问题

- 用户插入新想法时，何时应自动合并，何时应先询问？
- “持续责任”与普通周期任务应共用还是分开建模？
- 第一版优先选择本地常驻、云端常驻，还是本地与云端的混合控制面？
- 任务规划由模型动态生成到什么程度，哪些步骤需要确定性工作流？
- 什么情况下可以从用户输入隐式形成最小 Goal Contract，什么情况下必须显式确认？
- 不同 Goal 类型的最低充分 evidence 应由确定性策略、Executor 还是二者共同决定？
- 如何让用户理解 Pegas 的当前授权范围，而不把产品变成权限配置面板？
- 记忆写入是立即发生、任务结束后反思，还是两者结合？
