# Pegas Feature Map

> 状态：Living Document
>
> 更新日期：2026-11-21（DESIGN-002 搜索/触发历史/人工核对接入）

Feature Map 是 Pegas 的功能事实索引。任何功能开发开始前先查这里和代码，确认能力是否已经存在、权威实现在哪里、还缺什么；功能合入时必须同步更新对应条目。它不代替 Issue 或路线图，而是防止同一能力被不同入口重复实现。

## 状态定义

- **Planned**：只有明确需求，尚未形成可运行实现。
- **Scaffold**：接口或骨架已存在，但还不能构成用户闭环。
- **Partial**：主要路径可运行，关键场景、可靠性或体验仍缺失。
- **Usable**：目标场景可使用，有自动化验证和明确的事实来源。
- **Hardened**：经过故障、恢复、安全和运维验证，可长期依赖。

### ROUTE-001：控制意图路由验收边界（2026-11-21）

- **用户结果**：用户在主对话一句话内纠正正在执行的事情（“先别管排版，把数据整理对”）或明确取消（“这件事不用做了”），Router 将其识别为 `steer_task` / `cancel_task` 控制意图并持久应用；纠正不丢失、不被旧方向的执行结果覆盖，取消与显式停止按钮语义完全一致。
- **验收条件**：控制意图与 `create_task`/`continue_task` 共用同一持久 Routing Decision；模型只能引用候选集内的 Task，steer 仅允许 `started` 目标，无效判定回退确定性新建。queued Run 的纠正在同一事务合并进输入；running Run 的纠正持久挂在 Run 上，Worker 心跳续租与 steering 检测同事务，检测后中止 Executor、旧 Run 停放为 `superseded_by_steering:<id>`、后继 Run 复用同一 session 并携带纠正。带未消费 steering 的 Run 拒绝完成提交。cancel 复用 `stopTask` 的 human/stopped 事务（含 Approval 取消、authorized→unknown 核对、协作结算）。
- **非目标**：不实现 Idea、Trigger 控制意图；不做 Web 对话内控制反馈 UI；不新增独立控制 API（现有 `/stop` 命令保持不变）；不允许机器事件或协作 handback 铸造控制命令。
- **数据与权限边界**：控制意图只接受已认证人类 `user.message`；跨 owner 目标拒绝；等待审批等阻塞 Action 时 steering 抛 `TaskActionBlockedError` 走既有停放路径，不绕过 Action Policy。同一事件的决策幂等重放，冲突决策拒绝。
- **失败与恢复**：schema v24 新增 `steering_json` 与 `steering_of_run_id`（partial unique index 保证每个被纠正 Run 至多一个后继）；supersede 幂等。Worker 在 steering 中止后崩溃时，持久指令随后继 Run 恢复；存在未消费 steering 时 v24→v23 回滚被 Guard 拒绝，消费后放行。

### APPROVAL-001：持久审批与 Action 恢复验收边界（2026-11-21）

- **用户结果**：真实 Executor 在准备执行高风险 Action 时可以创建结构化 Approval；Run 立即释放 Worker。用户稍后从任意客户端批准、拒绝或要求修改后，决定经 Durable Event Inbox 唤醒原 Task，并由新的 Run 从保存的 Executor session、恢复点和 Action 上下文继续。
- **验收条件**：Approval 明确展示准备执行的动作、影响范围、互斥选项和默认建议；请求、决定和 Action 结果均支持幂等命令。只有当前 Run 的短期 claim capability 可以创建 Approval，只有 Task owner 可以读取和决定；任意客户端伪造的 `approval.decided` 事件不能恢复 Run。请求后原 Run 进入无 lease 的持久等待且 Worker 可领取其他 Task；决定事务性写入 append-only 审计记录与 Inbox Event；事件重放只产生一个 successor Run。进程在请求、决定、事件领取和 successor 创建之间重启后均可继续。批准只表示授权，不伪装成副作用已成功；Executor 必须另行记录 `succeeded`、`failed` 或 `unknown` Action outcome。
- **非目标**：本 Feature 不代替具体工具执行，不把 Router 变成权限判断器，不实现组织级 RBAC、多人会签、财务额度或凭证代理，也不允许 Approval 自身宣称外部副作用已发生。
- **数据与权限边界**：策略层只根据结构化 Action risk 决定是否必须审批；实际 Executor 负责在检查真实工具、参数和权限后生成用户可见文案。API bearer 保护用户读取与决定，Run claim capability 只允许写入其所属 Run；响应和 Outbox 永不回显 claim token。Action request、恢复点、决定和 outcome 均由服务端持久化，客户端只做投影。
- **失败与恢复**：重复请求返回同一 Approval；冲突 payload、过期/错误 claim、越权用户、非法选项和关闭 Task 均拒绝且不改变状态。决定写入后即使 Worker 崩溃，Inbox lease 过期可重领；应用决定采用唯一 decision/event/successor 约束防止重复恢复。`failed`/`unknown` outcome 保留显式外部状态，不允许普通 continuation、retry、Goal revision 或 Task 完成绕过；被 Action 阻塞的用户事件会持久停放，并在拒绝、修改或成功 outcome 后重新入队。停止 Task 会取消未决 Approval、将已授权 Action 标记为 `unknown` 并发出核对通知。回滚本 Feature 代码不删除 migration 数据，旧版本忽略新增表和列。
- **当前证据（2026-11-20）**：schema v16 通过 partial unique index 用 protocol version 隔离旧 scaffold，同时保留原始审计与幂等键；Approval 请求、Decision、successor Run、Action outcome、Outbox 与 owner 投影均持久化。Worker 把每次 claim 的短期 capability 和本机 Control Plane 地址传给 DSH，执行合同覆盖请求 Approval、等待 successor 和记录 outcome；传输强制使用 loopback，全局 bearer、恢复 token、模型密钥与父进程残留 claim 均不会继承。Electron 内置服务生成随机 bearer，并只对可信本机 origin 注入。测试覆盖 capability 先于 payload 的鉴权、owner 边界、伪造事件、精确重放、进程重启、approve/reject/revise、跨设备决定与单调轮询刷新、停止与核对通知、Goal revision、嵌套 Approval 与终态 Report 的 outcome fence、阻塞 continuation 的原子停放/释放/终止与唤醒、lease 过期、已记录 outcome 后的 Run 失败或 Task 停止、副作用未知、Task 级 Review Pack、分页、迁移冲突、HTTP、Web 待处理流程、fake DSH→真实 API→successor→outcome 重放、loopback capability 和桌面鉴权；完整门禁通过 33 个测试文件、327 个测试，statement 84.13%、line 87.03%，`pnpm check`、`pnpm smoke`、`pnpm smoke:desktop` 与独立安全/API/对抗审查通过。
- **人工核对更新（2026-11-21）**：schema v23 新增 append-only `action_reconciliations`（trigger 拒绝改写/删除，每 Action 一条，保存 resolution/note/核对前 status+result 快照/核对人）。owner 通过 `POST /v1/actions/:actionId/reconcile` 提交 `succeeded|failed` 结论：`succeeded` 把 Action 置为 `reconciled`、唤醒停放 continuation、允许 failed Run retry，并让 Review Pack 把该 side effect 计为已满足（附核对信息）；`failed` 保留人工确认的失败事实，继续阻塞 retry、Goal revision、协作与新 Approval。命令按 `commandId` 幂等重放，payload 冲突与二次核对返回 `409 action_reconciliation_conflict`，跨 owner/不存在返回 404；记录、Action 状态、Task 原因、唤醒与 `action.reconciled` Outbox 同事务提交。Task 停止后仍可核对 unknown Action 但不改写 ended 状态。存在 reconciled Action 时 v23→v22 回滚被 Guard 拒绝。`test/action-reconciliation.test.ts` 覆盖合同解析、unknown→succeeded 解锁、failed 结论持续阻塞、retry 解锁与幂等、重放/冲突/二次核对、跨 owner、过早核对、HTTP 401/201/409/404 与 Review Pack 完成链；`test/rollback-compatibility.test.ts` 覆盖 reconciled 拒回滚。
- **门禁证据（2026-11-21）**：rebase 至包含 DESIGN-002 修复与 DESKTOP-001 smoke 标题修复的 main 后，`pnpm check` 通过 51 个测试文件、492 个测试（statement 85.17%、branch 78.41%、function 90.15%、line 88.05%）；`pnpm smoke` 通过真实 Scheduler/Worker/notification/SQLite/HTTP 闭环，`pnpm smoke:desktop` 通过开发态 Electron 窗口 smoke。
- **为什么仍为 Partial**：通用 DSH tool-call 代理尚未把所有真实工具自动接入 Action Policy；第一版只强制约束已接入本协议的 Executor/工具适配器。由验证器主动探测外部状态的自动对账仍是后续 Feature。
- **Web 接入（2026-11-21，DESIGN-002）**：待你处理页对 `action.reconciliation_required` 通知显示「去核对」，打开核对抽屉展示动作类型/请求/结果并提交 succeeded/failed 结论（必填依据、commandId 幂等）；审批抽屉内 unknown/failed Action 同样可核对；已核对动作展示只读核对记录。真实服务端联调验证 unknown→succeeded 与 failed→failed 两条路径；证据见 DESIGN-002 搜索/触发历史/人工核对小节。

## Feature 开发协议

每次功能开发都遵循下面的顺序：

1. **先查重**：搜索本 Feature Map、架构文档和代码，确认是否已有相同能力或事实来源。
2. **确定归属**：复用现有 ID；确实是新能力时才新增 ID，并先写清用户结果、状态和权威实现位置。
3. **保持单一事实来源**：不同端只实现交互适配，核心状态和决策不得在 Web、iOS 或 macOS 分叉复制。
4. **先定义验证**：新增或修改自动化测试；修复缺陷必须增加能复现原问题的回归测试。
5. **完成质量门禁**：至少通过 `pnpm check`；涉及进程、数据库、通知或恢复路径时同时通过 `pnpm smoke`。
6. **同步地图**：合入前更新状态、实现入口、自动化证据和下一缺口，避免把 Scaffold 误标成 Usable。

## 质量阈值策略

覆盖率阈值是防退化基线，不是目标分数。当前全局最低值记录在 `vitest.config.ts`；新增功能应保持或提高覆盖率，不通过降低阈值来让 CI 变绿。每当关键低覆盖模块补齐测试后，随同该 Feature 提高阈值。

无用文件、依赖和导出由 Knip 阻断。确有动态加载或外部入口时，应在配置中写出最窄的显式例外，并在变更说明中解释原因。
