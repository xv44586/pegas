# Pegas Feature Map

> 状态：Living Document
>
> 更新日期：2026-11-21

Feature Map 是 Pegas 的功能事实索引。任何功能开发开始前先查这里和代码，确认能力是否已经存在、权威实现在哪里、还缺什么；功能合入时必须同步更新对应条目。它不代替 Issue 或路线图，而是防止同一能力被不同入口重复实现。

## 状态定义

- **Planned**：只有明确需求，尚未形成可运行实现。
- **Scaffold**：接口或骨架已存在，但还不能构成用户闭环。
- **Partial**：主要路径可运行，关键场景、可靠性或体验仍缺失。
- **Usable**：目标场景可使用，有自动化验证和明确的事实来源。
- **Hardened**：经过故障、恢复、安全和运维验证，可长期依赖。

### GOAL-001：目标形成与证据化交付（2026-11-20）

- **用户结果**：用户可以用不完整的愿望、问题、例子或语音开始；实际 Executor 帮助其澄清期望结果、关键上下文、前置条件、权限和完成标准。交付时，用户在 Outbox 按 success criteria 审查 evidence，而不是阅读代码、工具调用或处理过程。
- **验收条件**：Goal Contract 有来源事件和 revision；用户事实、Executor 推断与未知项可区分；Router 只归属 Task；Control Plane 只在当前 Goal revision 的必需 EvidenceRef 充分时完成 Task；Review Pack 逐项显示 `satisfied/partial/unverified/failed`、证据限制、剩余风险和回滚；视觉变化必须提供绑定最终 Artifact revision 的截图、关键帧或页面渲染；Outbox 聚合预览 evidence，并提供 Artifact、Channel 与按需审计入口。
- **非目标**：不强制简单任务进入长访谈；不新增用户必须理解的 Worker/Run/Goal Contract 操作对象；不把 Agent 总结、自由文本 `ready`、退出码、代码 diff 或日志洪流独立当作完成证据；不因本设计提升 `TASK-002`、`NOTIFY-003` 或 `QUALITY-001` 的当前状态。
- **数据与权限边界**：Goal Contract、EvidenceRef、Review Pack 和完成判断均以服务端为权威；evidence 继承用户、Task、Artifact 和敏感信息范围；目标扩张重新检查 Policy、成本、风险和 Mandate；客户端只负责预览、选择和下钻。
- **失败与恢复**：目标整理失败保留原始 Conversation Event；缺少上下文或权限时持久等待并释放 Run；evidence 缺失、失效或不匹配最终 revision 时相应 criterion 保持未验证；Review Pack 持久化后通知可独立重试，不能因投递失败删除证据或重复完成 Task。
- **当前证据（2026-11-20）**：schema v15 已持久化版本化 Goal Contract、Run Goal snapshot、Task Artifact、EvidenceRef、append-only verification event、Worker Report 与 Review Pack；所有写入和读取按 Task 所有者隔离。Goal 修订会原子重绑定 queued Run 或滚转到新 Run；当前 Run 的 `ready` Report 只有在每个必需 criterion 达到 evidence plan 的数量、kind、trust class 与 verification 要求时，才会在同一事务中完成 Run/Task、终止被取代的非终态 Run 并写入 `review.ready` Outbox。Report HTTP 写入由每次 claim 独有的 capability fencing；响应重试使用 Report 上持久化的 capability hash，过期 capability 不能创建新序号；DSH 子进程不继承实例 bearer、恢复 token 或模型密钥，只收到当前 Run 的短期 claim。执行完成后丢失 Worker 时，新 Worker 原地接管同一 Run 的 reporting phase，不重放 Executor 副作用；partial Report 会被后续 evidence/verification 重新唤醒。缺证、旧 revision、自证、跨 Task Artifact、错误 MIME 的视觉 Artifact、非当前 Run evidence 与冲突 attestation 均被拒绝或去重；同源 evidence 可在重试 Run 重新取证。旧库迁移、分页、响应重试、reporting lease 恢复和当前 Run 交付投影有自动化覆盖；最终门禁为 32 个测试文件、272 个测试，statement 83.42%、line 86.45%，`pnpm check` 与 `pnpm smoke` 均通过。
- **为什么仍为 Partial**：当前是服务端最小闭环，Goal 仍需由受认证调用方创建；DSH Worker 会为 Goal-bound Run 生成缺证的结构化 `ready` Report，避免执行完成后无报告卡死，但尚未自动形成可纠正的目标简报和带真实 EvidenceRef 的完整 Report。Artifact 内容尚未由独立验证器取证，普通 HTTP 用户主张只保存为 `pending`；高风险用户接受要等 `APPROVAL-001` 的受认证 confirmation capability。Web 也尚未把 Review Pack、视觉 evidence 与 validity 事件接到封板详情页。

### WORKER-001：事情范围执行配置与 Run 快照（2026-11-20）

- **用户结果**：每件事情默认跟随 Pegas 的全局 Agent 执行模型，也可以显式覆盖为某个 Provider/模型；用户能看出当前配置来自全局还是这件事情。修改只影响后续 Run，已经排队、运行或等待恢复的 Run 保留创建时的可解释快照。`WorkChannel` 只作为服务端 Task 详情投影的架构术语，不成为用户必须理解或配置的新对象。
- **验收条件**：服务端持久化按 Task 唯一、带 revision 的 WorkerProfile；owner 可以读取并以 optimistic revision 更新 `inherit`/`override`，相同 payload 重放不增加 revision，冲突 revision 不覆盖。Control Plane 在创建新 Run 时原子解析“Pegas 全局 Agent 默认值 + 事情级覆盖”，把 profile ID/revision、来源、最终模型、workspace、权限和协议写入 `execution_context_json`。配置不兼容时 continuation 创建新 Executor Session；兼容时才允许沿用旧 session。Worker 执行必须使用 Run 快照，不能在领取 queued Run 时偷换为此刻的全局设置。

### APPROVAL-001：持久审批与 Action 恢复验收边界（2026-11-20）

- **用户结果**：真实 Executor 在准备执行高风险 Action 时可以创建结构化 Approval；Run 立即释放 Worker。用户稍后从任意客户端批准、拒绝或要求修改后，决定经 Durable Event Inbox 唤醒原 Task，并由新的 Run 从保存的 Executor session、恢复点和 Action 上下文继续。
- **验收条件**：Approval 明确展示准备执行的动作、影响范围、互斥选项和默认建议；请求、决定和 Action 结果均支持幂等命令。只有当前 Run 的短期 claim capability 可以创建 Approval，只有 Task owner 可以读取和决定；任意客户端伪造的 `approval.decided` 事件不能恢复 Run。请求后原 Run 进入无 lease 的持久等待且 Worker 可领取其他 Task；决定事务性写入 append-only 审计记录与 Inbox Event；事件重放只产生一个 successor Run。进程在请求、决定、事件领取和 successor 创建之间重启后均可继续。批准只表示授权，不伪装成副作用已成功；Executor 必须另行记录 `succeeded`、`failed` 或 `unknown` Action outcome。
- **非目标**：本 Feature 不代替具体工具执行，不把 Router 变成权限判断器，不实现组织级 RBAC、多人会签、财务额度或凭证代理，也不允许 Approval 自身宣称外部副作用已发生。
- **数据与权限边界**：策略层只根据结构化 Action risk 决定是否必须审批；实际 Executor 负责在检查真实工具、参数和权限后生成用户可见文案。API bearer 保护用户读取与决定，Run claim capability 只允许写入其所属 Run；响应和 Outbox 永不回显 claim token。Action request、恢复点、决定和 outcome 均由服务端持久化，客户端只做投影。
- **失败与恢复**：重复请求返回同一 Approval；冲突 payload、过期/错误 claim、越权用户、非法选项和关闭 Task 均拒绝且不改变状态。决定写入后即使 Worker 崩溃，Inbox lease 过期可重领；应用决定采用唯一 decision/event/successor 约束防止重复恢复。`failed`/`unknown` outcome 保留显式外部状态，不允许普通 continuation、retry、Goal revision 或 Task 完成绕过；被 Action 阻塞的用户事件会持久停放，并在拒绝、修改或成功 outcome 后重新入队。停止 Task 会取消未决 Approval、将已授权 Action 标记为 `unknown` 并发出核对通知。回滚本 Feature 代码不删除 migration 数据，旧版本忽略新增表和列。
- **当前证据（2026-11-20）**：schema v16 通过 partial unique index 用 protocol version 隔离旧 scaffold，同时保留原始审计与幂等键；Approval 请求、Decision、successor Run、Action outcome、Outbox 与 owner 投影均持久化。Worker 把每次 claim 的短期 capability 和本机 Control Plane 地址传给 DSH，执行合同覆盖请求 Approval、等待 successor 和记录 outcome；传输强制使用 loopback，全局 bearer、恢复 token、模型密钥与父进程残留 claim 均不会继承。Electron 内置服务生成随机 bearer，并只对可信本机 origin 注入。测试覆盖 capability 先于 payload 的鉴权、owner 边界、伪造事件、精确重放、进程重启、approve/reject/revise、跨设备决定与单调轮询刷新、停止与核对通知、Goal revision、嵌套 Approval 与终态 Report 的 outcome fence、阻塞 continuation 的原子停放/释放/终止与唤醒、lease 过期、已记录 outcome 后的 Run 失败或 Task 停止、副作用未知、Task 级 Review Pack、分页、迁移冲突、HTTP、Web 待处理流程、fake DSH→真实 API→successor→outcome 重放、loopback capability 和桌面鉴权；完整门禁通过 33 个测试文件、327 个测试，statement 84.13%、line 87.03%，`pnpm check`、`pnpm smoke`、`pnpm smoke:desktop` 与独立安全/API/对抗审查通过。
- **为什么仍为 Partial**：通用 DSH tool-call 代理尚未把所有真实工具自动接入 Action Policy；第一版只强制约束已接入本协议的 Executor/工具适配器。`unknown` outcome 已阻止自动重试和 Task 完成，但自动对账与人工确认结果仍是后续 Feature。

### DESKTOP-001：macOS Electron 壳验收边界（2026-11-20）

- **用户结果**：用户可以从 macOS 应用窗口直接使用与 Web 封板一致的 Pegas；窗口关闭和重新打开不会产生第二套 Conversation、Task、Run 或设置状态。
- **验收条件**：Electron 主进程启动并监督仓库现有 Control Plane 与 Worker，使用 `app.getPath('userData')` 下的专用数据目录，等待健康检查后再展示 UI；窗口默认白底、尺寸与封板桌面布局匹配，支持最小尺寸、macOS 激活重开、外链交给系统浏览器和音频权限；`contextIsolation`、`sandbox` 开启且 `nodeIntegration` 关闭。开发构建可启动，macOS smoke 能看到 Pegas 主界面且无控制台错误，并留下桌面窗口截图。
- **非目标**：本 Feature 不复制服务端业务逻辑，不新增自动更新、签名/公证、菜单栏常驻、全局快捷键或原生通知，也不把 Electron 当作新的权威存储。
- **数据与权限边界**：Renderer 只能访问本机 Control Plane 的 HTTP 接口；不暴露 Node/Electron bridge。内置服务每次启动生成随机实例 bearer，Electron session 仅对可信本机 origin 自动附加，renderer 不读取或保存 bearer。麦克风只对本机 Pegas origin 的 audio 请求授权，摄像头、地理位置、通知和未知权限默认拒绝。外部 URL 不在应用内导航。
- **失败与恢复**：Control Plane 未就绪时显示可读启动失败页并允许退出；主进程退出时向子进程发送 SIGTERM，并在超时后升级；子进程数据继续由现有 SQLite 恢复语义负责。回滚本 Feature commit 即恢复纯 Web 构建，不迁移或删除用户数据。
- **当前证据（2026-11-20）**：Electron 开发态与 `releases/desktop/mac-arm64/Pegas.app` 打包态均通过真实窗口 smoke：从封板输入器提交消息、等待 Worker 完成 Run，再主动终止 Worker，确认产品页立即撤下并显示“服务已停止”。页面标题、无控制台错误、`contextIsolation`、`sandbox` 和关闭 `nodeIntegration` 的窗口配置均由自动化读取确认。ASAR 打包路径、可信 origin bearer 注入、回环 URL、独立进程组和覆盖 DSH 5 秒清理窗口的 SIGTERM→SIGKILL 退出升级有 11 个专门回归测试，首次设置遮罩也由 smoke 自动退出，应用使用封板蓝色 Pegas 图标。当前完整门禁通过 33 个测试文件、327 个测试，开发态 Electron smoke 通过。
- **发布边界**：当前 Candidate 是本机未签名目录包，适合 MVP 开发与验收；Developer ID 签名、公证、DMG/自动更新和原生通知不在 DESKTOP-001 范围内，进入分发前必须另建发布 Feature。

## Feature 开发协议

每次功能开发都遵循下面的顺序：

1. **先查重**：搜索本 Feature Map、架构文档和代码，确认是否已有相同能力或事实来源。
2. **确定归属**：复用现有 ID；确实是新能力时才新增 ID，并先写清用户结果、状态和权威实现位置。
3. **保持单一事实来源**：不同端只实现交互适配，核心状态和决策不得在 Web、iOS 或 macOS 分叉复制。
4. **先定义验证**：新增或修改自动化测试；修复缺陷必须增加能复现原问题的回归测试。
5. **完成质量门禁**：至少通过 `pnpm check`；涉及进程、数据库、通知或恢复路径时同时通过 `pnpm smoke`。
6. **同步地图**：合入前更新状态、实现入口、自动化证据和下一缺口，避免把 Scaffold 误标成 Usable。

## 质量阈值策略

覆盖率阈值是防退化基线，不是目标分数。当前全局最低值记录在 `vitest.config.ts`；新增功能应保持或提高覆盖率，不通过降低阈值来让 CI 变绿。每当关键低覆盖模块补齐测试后，随同该 Feature 提高阈值。

无用文件、依赖和导出由 Knip 阻断。确有动态加载或外部入口时，应在配置中写出最窄的显式例外，并在变更说明中解释原因。
